Persistence & Checkpointing Implementation

The workflow can now survive process restarts, resume an interrupted graph by thread ID, and expose current and historical state through one runtime contract backed by Postgres.

1. What changed

Graph became checkpoint-aware

build_supervisor_graph() now accepts a LangGraph checkpointer plus optional interrupt boundaries.

Persistence got one contract

The Postgres runtime exposes start, resume, get_state, and get_history.

Production storage was verified

Docker Postgres persists checkpoints across independent Python connections, not merely across calls in one process.

Boundary: this is workflow persistence, not long-term semantic memory. It records execution state for one thread; it does not retrieve preferences or knowledge across unrelated threads.

2. The core graph change

The graph definition remains storage-agnostic. Its builder accepts the abstract LangGraph saver contract and passes it into compilation. Therefore, graph nodes do not contain database code.

Why dependency injection matters

The graph owns workflow logic while the runtime owns Postgres. Nodes remain free of connection and schema-management code.

Why interrupts are compile options

An interrupt creates a known checkpoint boundary. Calling resume(thread_id) continues with the next scheduled node.

3. Thread identity and state continuity

LangGraph uses configurable.thread_id as the durable execution key. The implementation also writes that ID and run-level metadata into SupervisorState so the application can inspect them without parsing checkpoint internals. 

# src/writer_agent/persistence.py
def thread_config(thread_id, metadata=None):
    if not thread_id or not thread_id.strip():
        raise ValueError("thread_id must be a non-empty string")

    config = {
        "configurable": {"thread_id": thread_id.strip()}
    }
    if metadata:
        config["metadata"] = dict(metadata)
    return config
Field Where it lives Purpose
thread_id Runnable config + workflow state Find every checkpoint belonging to one workflow execution.
task_id Workflow state Application-level task identity; remains unchanged on resume.
run_metadata Workflow state Stores start time and caller-supplied context.
checkpoint metadata Checkpointer storage Stores LangGraph step, source, writes, and execution lineage.

4. Start, checkpoint, and resume lifecycle

  1. The caller chooses a new thread ID. One new user request should receive one new ID.
  2. start() checks for existing state. Reusing an existing ID is rejected before execution, preventing an old thread from being merged with a new request.
  3. The initial state receives identity and metadata. A UTC start timestamp, thread ID, and caller metadata are added before the first graph invocation.
  4. LangGraph checkpoints each state transition. The saver records channel values, pending writes, node position, and checkpoint ancestry.
  5. An interrupt or process failure stops forward progress. Already committed graph state remains in the selected database.
  6. resume() loads the latest snapshot. Invoking the graph with None means “continue this thread” rather than “start with new input.” 
# Shared runtime contract
def start(self, thread_id, state, *, metadata=None):
    config = thread_config(thread_id, metadata)
    if self.graph.get_state(config).values:
        raise ValueError("Thread already exists; use resume()")

    initial_state = {
        **state,
        "thread_id": thread_id.strip(),
        "run_metadata": {
            "started_at": datetime.now(UTC).isoformat(),
            **dict(metadata or {}),
        },
    }
    return self.graph.invoke(initial_state, config=config)

def resume(self, thread_id, *, metadata=None):
    config = thread_config(thread_id, metadata)
    snapshot = self.graph.get_state(config)
    if not snapshot.values:
        raise KeyError("No checkpoints found")
    return self.graph.invoke(None, config=config)

7. Docker Postgres implementation

compose.yaml provides a reproducible local database with a health check, host-only port binding, and a named volume. 

# compose.yaml
services:
  checkpoint-db:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: writer_agent
      POSTGRES_USER: writer_agent
      POSTGRES_PASSWORD: writer_agent_dev
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - writer-agent-postgres:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U writer_agent -d writer_agent"]
      interval: 2s
      timeout: 3s
      retries: 15

Host-only exposure

Binding to 127.0.0.1 avoids exposing the development database on every network interface.

Named volume

Container replacement does not delete checkpoints. Explicit volume deletion is required to discard them.

Development credentials only: writer_agent_dev is committed for local Docker convenience and must not be used for an externally reachable database.

9. Inspection API

Latest state

get_state(thread_id) returns a StateSnapshot containing values, next nodes, tasks, configuration, and checkpoint metadata.

Execution history

get_history(thread_id) returns snapshots newest first, supporting debugging and state-transition audits. 

with PersistentWriterAgent() as agent:
    current = agent.get_state("report-rag-001")
    history = agent.get_history("report-rag-001")

    print(current.values["status"])
    print(current.next)
    print(len(history))

10. How continuity is tested

The decisive Postgres integration test uses two independent runtime contexts. The first stops after initialization and closes its database connection. The second opens a new connection, resumes the same thread, and verifies identity and state. 

# tests/test_postgres_checkpointing.py — simplified
with PersistentWriterAgent(
    database_url,
    interrupt_after=["initialise_task"],
) as runtime:
    interrupted = runtime.start(thread_id, request_state)
    task_id = interrupted["task_id"]

# The first Postgres connection is now closed.
with PersistentWriterAgent(database_url) as resumed:
    completed = resumed.resume(thread_id)
    assert completed["task_id"] == task_id
    assert completed["status"] == "escalated"
    assert len(resumed.get_history(thread_id)) >= 3
Verified result: 14 tests passed, including the real Postgres cross-connection resume test. The separate live Groq/Tavily test remained intentionally opt-in.

13. Design decisions and remaining boundary

Decisions that protect correctness

  • New requests cannot silently reuse an existing thread.
  • Resume passes no new graph input.
  • Storage selection does not leak into graph nodes.
  • Owned database connections close via context managers.
  • Strict MessagePack decoding is documented for checkpoints.

Explicitly outside Phase 2

  • Semantic retrieval and vector search.
  • User preferences shared across threads.
  • Project knowledge or accepted-output memory.
  • Human approval interfaces.
  • Parallel subtask dependency execution.
Phase 3 handoff: long-term memory should use separate tables or stores and an explicit retrieval policy. Checkpoint tables should remain an execution concern, not become an application knowledge database.
